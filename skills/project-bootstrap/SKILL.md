# project-bootstrap

开工前十分钟，决定这个项目后面是「能接上手」还是「每次从零考古」。

## 什么时候铺

- 新项目，第一次提交之前。
- 接手一个已经有代码但没文档的仓：先铺 DESIGN 和 PITFALLS，再读代码。读完再写，写下来的全是代码里已经有的——那部分不需要记。
- 要把活派出去（另一个会话、另一台机器、另一个人）：只铺 CARD。

## 怎么铺

```bash
./bootstrap.sh <目标目录> --name <项目名> [--only missing]
```

已有文件不覆盖。填不进去的节直接删——留空比留废话好。

## 五份文件，每份只回答一个问题

| 文件 | 回答 | 判据 |
|---|---|---|
| `AGENTS.md` | 接活的怎么进来、怎么交、卡住怎么办 | 一页。读不完的说明写虚了 |
| `tasks/*.md` | 这一件事的目标 / 范围 / 验收 / 失败 | `verify` 必须是命令 + 期望输出 |
| `DESIGN.md` | 现在什么样 | 只写契约（不变量、口径、缺口），不写教程 |
| `DECISIONS.md` | 为什么这么定、否掉了什么 | 没写否选项的，不算决定 |
| `PITFALLS.md` | 哪里会静默骗人 | 只收「不报错但结果是错的」 |

## 三条硬判据

1. **验收要么能机器检查，要么承认没收。** 形容词不是验收。
2. **台账只记沉默失败。** 会报错的不记——报错自己会说话。
3. **决定必须带否掉的选项 + 什么条件下该重看。** 否则半年后同一场讨论再来一遍。

## 判断一份"提示词/skill"值不值

拿到任何一份声称能让"下一个会话直接做到"的提示词，按这四条验：

1. 里面有几条「因为……所以不做 X」？一条都没有 = 需求文档。
2. `verify` 是可执行命令，还是形容词？
3. 它冻结的是哪一层（概念 / 信息架构 / 交互 / 视觉语法 / 令牌）？冻结越靠上，产出越像执行。
4. 踩坑那条是「症状 + 根因 + 验证命令」，还是「注意一下 X」？

四条都不过，那份提示词搬不动能力，只搬得动形状。

## 反模式

- 把成品倒推成步骤清单 → 下一轮像执行。
- PITFALLS 写成 changelog → 混了「做了什么」，就没人查「哪里会骗人」。
- DESIGN 写成教程 → 教程会过期且没人管；契约一过期就是 bug。
- 卡的范围写成「优化一下 X」→ 返工。范围要窄到能一眼判断越没越界。
